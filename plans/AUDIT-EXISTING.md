# 已有服务器的独立只读审计

`audit.py` 用于核验已经手工加固、使用旧 apply 方案或已经由新版管理的机器。它不要求 `/var/lib/reinforce-my-ssh` 已存在，不会创建或更新该目录，不会接管配置、安装文件、加载 nft、启停单元或重启服务器。

## 执行方式

先用普通管理账户登录，在服务器中 sudo 执行，不需要开放 root SSH 登录：

```bash
ssh example-host
sudo python3 ~/ssh-apply/audit.py \
  --port 2222 --user deploy \
  --allow 203.0.113.0/24 \
  --allow 2001:db8:1234::/48 \
  --closed-port 22
```

示例地址、端口和账户必须替换。默认就是只读模式，不需要 `--dry-run`，不接受 `--apply`。主机需要 Python 3、OpenSSH server、iproute2、nftables、systemd 和 journal；缺少工具或完整读取权限会显示证据不足。

`--port`、`--user`、至少一个 `--allow` 是必填的显式审计目标，不从新版 policy 自动继承，也不从当前配置反推“当前值即正确值”。`--allow` 会规范化、去重；带主机位的 CIDR 被拒绝。

`--closed-port` 可重复，明确指定必须无 TCP 监听的端口。未传就不检查旧端口，报告中的 policy 会显示空列表；不要把部署参数 `--old-port none` 当作确认 22 关闭的证据。

其他参数：

- `--format json`：输出机器可读报告；重定向保存由操作者决定，脚本本身只输出 stdout。
- `--source IP`：补充要采集的 sshd 来源上下文，可重复；默认优先当前 SSH 来源，无当前会话时采集回环样本。
- `--firewall-unit custom.service`：指定实际加载器；默认识别新旧防火墙服务名。两个都存在时不会猜测唯一所有者。
- `--nft-table name`：指定实际 inet 表名，默认 sshguard。
- `--sshd-config /absolute/path`：指定磁盘解析入口；非默认入口与存活主进程的关联默认保留为未知。

不要给 `/usr/bin/bash` 配 NOPASSWD 来模拟“只读 sudo”；那会允许任意 shell 命令提权。本工具也不管理 sudoers。

## 结果含义

报告分开显示四类结论：

| 字段 | 含义 |
| --- | --- |
| 安全效果 security_result | 当前显式审计目标的通过、不符合或证据不足，不由配置文件名或纳管状态决定 |
| 管理归属 ownership | 新版记录、旧方案痕迹、未纳管或未知；存在新版记录也不代表配置安全 |
| 迁移准备 migration | 阻断列表或未评估；不代表允许执行 apply，也不代表迁移备份已经齐全 |
| 重启证据 reboot | 核对新版 pre/post 元数据与 boot/配置的一致性，或证据不足；本次不执行重启 |

退出码：0 为本次范围已证实通过；1 为至少一项已证实不符合；2 为没有明确不符合但存在权限、采集或支持范围不足。明确不符合与证据不足并存时返回 1，仍保留每一项证据。

安全效果通过不代表公网、云安全组、拒绝来源外测或真实重启已完成；这些范围会在报告中说明，重启记录单独列出。无新版记录不会使安全效果自动失败。

## 如何核验及支持边界

- 使用 `sshd -t/-T -C` 解析实际 Include 与认证值，接受旧配置位置。仅禁 password 不足以证明公钥专用；同时核验键盘交互、root、公钥和其他认证方法。存在活动 Match 时保留上下文样本，但不冒充所有分支已覆盖。
- 核验实际监听、禁止端口和额外 SSH 端口。允许单个 IPv6 双栈 socket；使用 `ss -e` 的内核 v6only 标记证明覆盖关系，不仅凭当前 sysctl 或固定两个监听来判断。
- 读取完整 nft JSON，对支持的单 input/filter 链按顺序求值，用全部 CIDR 边界划分来源区间，核验允许/拒绝的新连接。不只搜索 accept/drop 字样，不要求链名或文件名固定。已建立连接的放行不等于白名单被撤销。
- 自动解释源地址、TCP 端口、ct state、lo 接口、nfproto 及 accept/drop/reject。命名集合、跳转、映射、复杂接口条件、多链交互等当前保留未知。其他前置/input 链可能继续拒绝，不能只看一条链的额外 accept 就断言最终可达。
- 旧规则仅按回环源地址放行而不约束 lo 时，防伪造路径没有自动证明，显示证据不足；这不会仅因“旧文件”而判定不符合。
- 核对 socket 与实际防火墙加载服务的持久启用、有效启动依赖，使用 `systemd-analyze verify` 检查启动图，不执行服务。已知顺序环判不符合，无法解释的传递依赖保留未知。
- 自动证明纯 oneshot、无额外前后置命令、失败不会被忽略的直接 `nft -f` 或单条 `exec nft -f` 加载器，并比较其引用磁盘文件与当前内核表。循环、先删表、额外 shell 操作等复杂旧加载器保留未知，不执行它们来试验。
- 结合主进程、启动参数及文件时间核验当前磁盘配置与进程关系。配置晚于启动或存在入口/参数覆盖时，缺少可靠重载证据就保留未知。
- 当前公钥通道证据来自同 boot 日志 PID、存活 SSH 四元组及 sudo 祖先进程链。需要目标用户在实际外部新端口 SSH 会话中直接 sudo 执行；控制台或 tmux 等路径可能无法获得足够证据。
- 旧版历史重启记录不自动导入新版 verified。只有当前本机新记录、配置摘要、pre/post boot 和事务字段一致时，报告“记录一致”；它仍不是本次实际执行了重启，也不是第三方证明。

这些未知项是明确的核验范围，不能通过创建假的 state、跳过解析或放宽 apply 检查消除。可以据此安排有针对性的人工复核。

## 与三个部署脚本的关系

stage1 默认是部署前提检查；stage2/stage3 默认是受管状态复验。未纳管时它们不再把缺少新版阶段误写成服务器未加固，而是提示独立审计并返回非零。所有 apply、confirm 和 rollback 的保护仍保留。

上传脚本现在同时上传 audit.py，只说明上传完成，不再无条件建议所有机器执行 stage3。当前旧服务器不迁移的决定保持不变；本轮没有实现 adopt/迁移入口。
