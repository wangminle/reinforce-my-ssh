# 旧方案已加固、新版脚本拒绝检查的原因与方案

日期：2026-10-25。

本轮依据：用户粘贴的上传、远端只读执行记录，当前三脚本源码、上传脚本及旧版仓库实现。本轮未连接远端、未执行上传或 apply，以下不冒充新的远端实测。

## 结论

目前返回的失败不能解释为服务器未加固。它说明现有服务器不符合新版工具的接管前提，也没有建立新版权威状态。

写入前拒绝接管未知配置有必要；把这类拒绝当作服务器安全不合格则不成立。重构后的脚本同时承担部署前提、工具状态和安全效果的检查，却缺少独立于新版状态目录的现状审计入口，属于能力与诊断语义上的缺口。

另一方面，记录中的“旧方案已完成同等加固”不能直接扩展为“已重新验收新版所有安全目标”。这不否定管理员以前做过加固或重启，只说明本轮证据尚未覆盖这些完整目标。

## 1. 每一条失败实际证明什么

| 实际输出 | 源码依据 | 可以得出的结论 | 不能得出的结论 |
| --- | --- | --- | --- |
| 6 条非受管指令 | stage1.sh 的 scan_sshd_config，仅按指令名及路径拒绝；不判断参数是否更安全 | 旧配置不由新版指定文件管理，自动写入前需要解决所有权与冲突 | root 登录或密码认证仍然开启 |
| 当前来源在 ALLOW 内 | require_source_allowed 对本次传入参数做 CIDR 包含判断 | 当前连接来源满足传入白名单 | nft 内核已经完整执行该白名单，或其他来源全部被拒绝 |
| stage2 请先完成 stage1 | 主入口依据 STATE_STAGE 闸门，未纳管时提前退出 | 新版 stage1 事务未登记 | 服务器还未关闭密码或旧端口 |
| stage3 策略文件不可读 | 先 load_policy，再加载状态/摘要，之后才 run_checks | 当前不能按新版权威策略执行复验 | 本次已经检查发现重启、防火墙或认证失败 |

所以，stage2/stage3 此次根本没有完成其安全效果检查，结果应描述为“未纳管，未执行该项复验”，而不是两项安全验收失败。stage1 最后一行来源检查为 OK，也不能覆盖前面扫描器的失败。

## 2. 重构前后检查对象变了

旧版仓库中的 stage3 主要通过 detect_stage 观察 ssh-firewall.service、nft、认证和旧验证文件来推断 S0–S3。新版改为 policy.conf、state.conf、事务、配置摘要以及明确的外部确认。这能防止拿不完整运行事实伪造阶段完成，也能约束回滚范围，但无法自动识别旧 apply 系列建立的状态。

远端旧 apply 的具体内容未在本轮重新获取，不能把旧仓库版本当作远端实现的精确副本。

上传脚本只有 mkdir、scp 和校验和比较。上传新版脚本不会创建 policy/state，不会运行阶段转换，也不会把旧配置改成新版布局。它最后无条件建议执行新版 stage3，遗漏了未纳管机器不具备此前提的情况，需要修正指引。

当前 verify_runtime 还要求五个受管文件与生成模板逐字一致、固定防火墙单元名、特定 socket 地址集合及 BindIPv6Only。这些适合验证“本工具写出的配置是否漂移”，不适合作为所有已有安全部署必须采用的唯一布局。

## 3. 非受管指令不等于不安全指令

扫描器遇到主文件中的 PermitRootLogin no，也会拒绝。no 与 yes 在这个所有权检查中没有区别。

判断实际认证策略需要由 sshd 按真实配置入口、Include 和连接上下文解析。OpenSSH 通常采用先读到的值，Include 在所在位置展开；不能笼统说后面的文件覆盖前面的文件。Port 等可重复指令又有各自规则，不能用统一的文本覆盖逻辑猜测。

依据：[OpenSSH sshd_config 手册](https://man.openbsd.org/sshd_config)。当前磁盘解析结果也不等于运行中的主进程已加载这些值，应结合实际启动参数、进程及新的认证连接验证。

主文件的重复设置可以是维护风险和未来漂移风险，但应与当前已证实的认证漏洞分开报告。有效值安全时，不应仅因为文件名不同就把安全效果判为失败。

## 4. 已有信息与待补证据

粘贴记录中的直接终端输出确认了旧指令位置、当前来源符合传入 ALLOW，以及新版阶段/策略闸门阻断。前一位助手另报告了仅监听 62206、22 关闭、root/password 为 no、旧防火墙单元 enabled 和 nft 表存在；本轮把这些作为已有记录引用，不当作新采集证据。

独立复核至少应覆盖：

1. 指定非 root 用户的新连接确实用公钥完成，且 sudo 可用；明确公钥专用策略，不能只观察 PasswordAuthentication no 而遗漏键盘交互等路径。
2. 在适用的 root、管理用户、来源和本地地址上下文中核对有效认证配置；存在 Match 或其他 Include 布局时完整解析，无法覆盖的分支记为未知。
3. 实际监听及进程归属、新端口的必要 IPv4/IPv6 路径、明确禁止的旧端口是否关闭。不能以“只允许两个固定通配 socket”替代对已有监听方案的语义核验。
4. nft 的实际 hook、优先级、来源、端口、放行/拒绝路径及其他规则交互；仅存在 sshguard 表不足以证明白名单有效。
5. 旧加载器的真实文件、启动依赖及有效单元图；enabled 不能证明防火墙在 SSH 开放前已经加载，也不能证明重启过程中没有顺序环。
6. 历史重启记录及当时配置/boot 的关联。当前可登录、单元 active、enabled 都不能单独证明此前配置已跨重启验收。旧记录若仍存在，可保留为历史旁证，不直接伪装成新版 verified。

systemd 会合并各层 unit/drop-in，实际依赖和属性需要读取有效配置；[systemd.unit 文档](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)说明了加载路径和 drop-in 合并方式。

另一个参数细节：--old-port none 表示候选流程不保留旧入口，不等于独立审计已经确认 22 关闭。现有代码也会跳过旧端口检查。审计应单独声明禁止的端口，例如 closed_ports=[22]，不要把迁移参数当成验收证据。

## 5. 建议方案

### 方案 A：旧机器保持原方案，增加独立只读审计，优先采用

沿用已有 ADJ-001 的决定，不为得到绿色输出而重跑部署。增加独立 audit 入口，允许从显式用户参数或外部审计策略读取目标，不要求新版 state/policy，也不隐式创建它们。

审计分三类结果：

- 安全效果：通过、明确不符合、证据不足；每项附实际值与证据。
- 管理归属：新版管理、旧方案管理、未识别；旧方案管理本身不是安全失败。
- 迁移准备：可以迁移或存在阻断；阻断列表独立展示，不覆盖安全效果。

重启证据再独立报告为旧证据、当前验证或未知。没有证据就保留未知，不能靠新建状态文件变成通过。

审计可检查旧 ssh-firewall.service、旧 socket override 等实际有效配置；只读模式接受满足同等安全目标的不同布局。仍然保留 apply 路径对文件所有权、复杂配置和回滚范围的严格限制。

建议退出码只表达当前审计任务：0 为已证实满足目标，1 为存在已证实不符合项，2 为权限、证据或支持范围不足。是否可被工具接管应作为独立字段，而不是混用安全退出码。

先修正默认检查的诊断文字和上传后的指引：明确“这是部署预检/受管复验”，未纳管时说明未执行安全审计，不再把 stage3 描述为通用服务器验收入口。

### 方案 B：需要新版生命周期管理时，再做专门迁移

迁移应有独立入口与事务，而不是删除几个文件后直接假装从空白机器开始。

先完成方案 A 的只读采集，在维护窗口准备独立救援并保存所有将修改的文件、旧加载器、单元状态和实际 nft。再制作确定的迁移计划，明确哪些主文件指令、drop-in 和旧单元由谁管理。

迁移重点：

- 只迁移目标指令，不批量删除所有 SSH drop-in，保留无关业务配置。
- 旧 override.conf 可能晚于新的 00-reinforce-my-ssh.conf 生效，应处理其有效属性，不只看新文件是否已写入。
- 旧、新加载器可能修改同一个 inet sshguard 表。明确唯一加载者及启动关系，避免下次启动时旧服务把新规则覆盖。
- 保护现有已关闭端口，不因默认 OLD_PORT=22 在迁移中重新开放；候选配置必须在完整白名单下生效。
- 修改范围内的全部旧配置都应进入迁移备份；现有 stage1 只备份五个受管路径，不能为额外删除主配置或旧 drop-in 提供完整回滚。
- 外部新会话验证后才完成接管；历史部署不冒充新版 candidate-ready/hardened/verified。接管导入事实与本轮验证事实要区分，重启验收另做。

### 不建议的处理

不要手工伪造 policy.conf/state.conf、把 STAGE 改成 verified、仅靠忽略非受管指令放开 apply，或为解决 sudo 问题授予 /usr/bin/bash 的 NOPASSWD。后一种会允许任意 shell 命令获得 root，无法做到只读授权。管理员在现有会话中执行限定的采集命令更合适。
