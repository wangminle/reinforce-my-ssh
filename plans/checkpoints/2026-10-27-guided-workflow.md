# 按状态检查、执行与续跑

## 需求与交付

用户要求脚本兼具执行和提示：先摸清现状，能执行的阶段直接推进；权限、必要输入或外部操作缺失时，给出具体命令。保留四个工作文件，不增加独立运行文件。

已实现统一 `--guide`：默认 stage0 仍只读，并新增 next_step；显式向导根据实际 state/policy 调用同目录阶段脚本。stage1/2/3 的 `--guide` 转入统一入口，不要求用户判断自己应从哪个阶段继续。

```bash
# 服务器中运行；example-host 是客户端使用的地址或 SSH 别名
sudo bash ~/ssh-apply/stage0-audit.sh --guide --host example-host
```

初次运行按需询问目标端口、非 root 用户和允许来源 CIDR；不会把动态当前来源自动当成安全策略。也可用 --port/--user/--allow 或 --conf 提前声明。普通用户在交互终端自动交接 sudo；无权限、无 sudo 或无终端时给出完整命令，不建议通用 shell NOPASSWD。

## 推进边界

1. 未纳管：stage1 --apply，常规旧配置由事务迁移处理，不要求事先手工改为加固终态。
2. 候选待确认：新外部公钥会话中 stage1 --confirm，成功后继续 stage2 --apply。
3. 收口待确认：再次建立新外部公钥会话，stage2 --confirm，成功后继续 stage3 --apply。
4. 重启待验：同 boot 只提示管理员自行重启；跨 boot 后续跑 stage3 --verify。
5. 已验证：当前 boot 由 stage3 完整复验后才报告完成；其他 boot 开始新的基线周期。

每次 apply 后明确暂停，打印强制公钥重连、服务器端续跑和可用回滚命令，不在原会话内紧接着 confirm。向导只是调用入口，原阶段的锁、摘要、外部连接、公钥日志与 sudo 校验继续生效。

每步非零、预期状态未推进或重新读取的策略损坏，立即停止。失败后重新读取实际状态给出恢复命令；依赖缺失时列出管理员安装命令，账户缺失时列出 adduser/usermod 及公钥准备提示，不擅自安装软件、创建账户或修改 sudoers。复杂 Match/加载器等仍需具体处理，不能为了推进而放宽保护。

## 修正的边界细节

- Python 源码通过 heredoc 输入，用户交互改读 `/dev/tty`；阶段子进程也连接真实终端，防止确认或 sudo 输入读到 EOF。
- 配置作为 KEY=VALUE 数据解析，命令通过 argv 执行，无 shell/eval。
- 首次配置可以不完整，交互补齐后形成权威策略；后续阶段不再把初始部分配置传给 stage3。
- 默认检查将实际观察到的连接传入 next_step，避免已在目标会话却一律提示连接错误。
- 无终端默认只给提示；显式 --yes 才可执行，首次仍须配置 RESCUE_CONFIRMED=yes。
- `--host` 只生成客户端提示，不猜测公网地址，不用于远程执行。
