## 1. 优先调整白名单加载方式

记录第 3.4 节的 unit 使用两个独立命令：先删除 `inet sshguard`，再读取规则文件。这使每次 restart 都有一个该表不存在的窗口；若第二步失败，旧规则不会自动回来。此时目标端口是否实际公网可达还取决于云安全组和其它防火墙链，不能断言必然暴露。

建议把“确保表存在、删除旧表、完整重建”组织为同一次 `nft -f` 提交，仅管理 `inet sshguard`，先验证再应用；首次加载、重复加载、扩大/缩小白名单和故意输入错误都需要在隔离环境验证。增加 `ExecReload` 后再提供日常 reload 指令。不要仅删掉 `ExecStartPre`：当前规则文件重复加载会追加规则，可能被旧 drop 遮蔽，见 [[BUG-045]]。独立加载器可以继续采用，避免触发既有全局配置的 `flush ruleset`，但不应原样推广当前两步加载方式。跟踪：[[ADJ-012]]。

`nft -c` 只检查命令有效性，不证明外部连接可用；oneshot 的 active 状态也不能代替检查内核规则。参见 [nft 官方手册](https://netfilter.org/projects/nftables/manpage.html)。

## 2. 修正开机顺序的保证范围

`Before=ssh.service` 在两个启动任务均存在时提供顺序，不能保证白名单加载失败时 SSH 不启动，也不会单独拉起白名单服务。记录里“避免白名单空窗”的说法应限定为正常启动路径，运行中 restart 的窗口另见上项。[systemd 官方依赖说明](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#Before=) 区分顺序与需求依赖。

结合本项目失联事故，不宜直接增加会在防火墙失败/重启时联动停止 SSH 的强依赖。先完成云安全组收口、保留已验证的控制台，再设计加载失败的明确提示和救援行为。如支持 socket 激活，还要覆盖 `ssh.socket`，不能只考虑 `ssh.service`。跟踪：[[ADJ-012]]。

## 3. 备份必须覆盖实际使用的加载器

将 `ssh-allowlist.service` 纳入备份是必要补充，但更新记录已将其改为“辅助脚本额外保存，待 sudo 确认”，本次也因 sudo 需要密码而无法核实。当前生成的恢复程序没有恢复它的文件、drop-in 和启用状态；重启后可能仍运行另一套策略。记录第 6.3 节的手工补救只覆盖 unit 缺失，而且 `enable --now` 对已经 active 的 oneshot 不会重新加载规则。

建议备份清单显式记录实际加载器的文件、active/enabled 状态及不存在的情况；恢复分别核对磁盘文件、定向 nft 表和开机加载状态。保留原有无关表，不全量回灌包含 Tailscale 动态表的 ruleset。恢复演练在隔离环境完成后，才将“备份齐全”升级为“已验证可恢复”。跟踪：[[ADJ-013]]。

更新记录明确本次未单独保存 `iptables-save` / `ip6tables-save` 输出，因此不能声称有全量 iptables-nft 回滚点。若后续补采，应标明实际采集时间，避免把当前状态冒充 10 月 30 日的历史状态。记录第 6.4 节的 `sudo iptables-save > <备份目录>/iptables.v4` 由未提权的 shell 执行重定向，在 root-only 目录会失败；应由 root shell 执行写入，或使用带管道失败检查的 `sudo tee` 方式。此处仅指出文档问题，本次未补采或改写远端备份。

备份还要标明用途：`20261030-204057-3795` 是加固后的稳态快照，不是退回加固前密码登录状态的基线。此前两份结构不完整，`20261030-202134-618960` 也已处于认证收紧后；不能依据时间较早就认定适合回滚到初始状态。

## 4. WebTerminal 先验证需求和来源，再决定授权

WebTerminal 尚未成功登录，却预先放行整个 `100.64.0.0/10`，且为了让检查器通过而省略入口接口限制。这一经验应推动改进检查器，而不应成为放宽实际策略的理由。该网段属于共享地址空间，地址属于该范围本身不能证明流量来自 tailnet 或指定云代理。

若需要 WebTerminal，先核对云厂商适用于该地域/产品的官方来源说明，确认非默认端口和公钥认证，再核对真实入站接口及来源。优先使用已确认且足够的范围，必要时限定实际接口；不能未核实就照抄 `eth0`。若不需要该入口，取消这项预授权。当前未取得官方来源说明，本复盘不确认记录中的两个云代理网段仍然适用。跟踪：[[ADJ-014]]。

同样，整个 VPC `/20` 的授权范围应由管理需求决定；若只有固定管理机需要进入，可以缩小到对应地址。tailnet 接口放行仍受 tailnet 访问策略和 SSH 公钥认证共同约束。

## 6. 检查器的跨重启判断需要修复

`stage0-check.sh:654` 和 `stage2-lockdown.sh:527` 的 `reboot_facts` 排除了 `/etc/ssh/sshd_config`，也未采集本次自建的 `/etc/systemd/system/ssh-allowlist.service`。因此“本次启动晚于全部加固文件修改”的证据范围不完整。

本轮使用现有内存桩件复现：启动时间设为 `1000000000`，白名单文件 mtime 为 `999999999`，主配置和 unit mtime 为 `1000000001`；两个函数仍返回 `booted_after_hardening=True`。这是聚合判断的覆盖遗漏，不推翻记录里已经实际发生的重启和登录。跟踪：[[BUG-048]]。

建议把实际生效的 SSH 主配置、包含文件、socket/service drop-in 和防火墙加载器纳入证据清单；读取失败明确返回未知。mtime 只作辅助，最终仍需当前 boot 的加载日志和新会话证明。
