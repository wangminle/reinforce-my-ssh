## 原始问题、原因与解决方案

### 1. 非 root 检查崩溃及证据误判（BUG-026）

- **现象**：读取受限备份路径时抛出 `PermissionError`；进程归属不可见时误报新端口未监听、旧端口已关闭；host key 无权限读取又被当作配置损坏，退出 1。
- **原因**：`System.exists()/is_dir()` 未把权限异常转换成证据异常；采集层没有 OSError 兜底；把“没看到”当成“不存在”，并在非 root 情况下运行需要特权的 `sshd -t`。
- **方案**：三个脚本统一路径异常处理；stage0 非 root 跳过 host key 校验，将不能证实的监听和认证标为 unknown，返回检查不完整的退出码 2。保留可从有效 socket 状态证明的正向监听事实，不把所有非 root 证据一律丢弃。

### 2. 备份快照写错目录、完整性门槛不足（BUG-027）

- **现象**：原指导输出 `sudo sh -c 'nft list ruleset > $DIR/nft-ruleset.nft'`；外层 DIR 没有导出，子 shell 通常将快照写到 `/nft-ruleset.nft`，UFW 和服务快照也存在相同问题。备份目录有一份 sshd_config 就被判为完成。
- **原因**：单引号阻止外层展开，子进程又收不到普通 shell 变量；验证门槛没有覆盖实际恢复需要的文件。
- **方案**：把备份根目录作为位置参数传入 `sudo sh -eu -c`；目录在该 shell 内创建，任何复制或快照失败立即停止。核验主配置、服务快照、配置目录副本或 `.absent` 记录、防火墙快照或工具缺失记录，以及最后才写入的 `backup-complete`。有半份备份不能解锁后续步骤。

### 3. 公钥认证检查假阳性（BUG-028）

- **现象**：构造 `PubkeyAuthentication no` 与 `AuthenticationMethods publickey`，原认证步骤和“公钥认证生效”检查仍可能通过。
- **原因**：采集到了公钥启用状态，判定时却只使用 AuthenticationMethods。
- **方案**：认证步骤和最终清单同时要求公钥认证明确为 yes，生成配置显式包含 `PubkeyAuthentication yes`。继续保留 `sshd -t` 和新公钥会话验证。该复现证明判定函数有缺陷，不代表真实 sshd 一定接受这种矛盾配置或能让整机验收通过。

### 4. stage1 过渡规则与 stage2 白名单冲突（BUG-029）

- **现象**：stage1 添加新端口的全来源允许；stage2 只追加限定来源和拒绝规则，没有清理旧规则。UFW 可继续匹配前面的全来源允许，nft 检查器也会因旧 accept 保持不通过。
- **原因**：阶段交接缺少过渡规则的收口步骤，未处理既有规则顺序。
- **方案**：UFW 先用 `insert 1` 插入声明来源允许，再添加拒绝、验证新公钥会话，最后删除全来源允许。nft 先安装受限链，再根据 stage1 注释、端口、规则形状和 handle 精确删除过渡规则；其它规则只提示人工核对，不清空 ruleset。
- **复核修正**：nft 跨基链 accept 不能绕过 drop，因此旧 accept 存在或检查失败，不足以单独证明公网开放。当前检查器仍保守拒绝未清理的宽泛规则。

### 5. 危险权限和错误属主仍显示账户完成（BUG-030）

- **现象**：原账户步骤只要求账户、sudo 组和公钥存在；0777 目录、0666 公钥文件及错误属主仍可显示 done，文本承诺的 chmod/chown 指令也未生成。
- **方案**：统一检查家目录、.ssh、authorized_keys 的属主和危险写权限；不安全或证据不足时账户不完成，并阻止切端口。生成精确、非递归的 chmod/chown 指令；stage2 同样使用账户安全事实。
- **复核修正**：0755/0644 等安全但偏离项目建议值的权限，不等于 OpenSSH 必然拒绝。区分安全要求与目录 700、文件 600 的收紧建议；不直接照抄递归 chown，也不假设主组名必然等于用户名。

### 6. 主配置旧 Port 残留和无效占位配置（BUG-031）

- **现象**：传统服务模式只重写 `10-newport.conf`，主配置或其它 drop-in 中的 `Port 22` 仍存在；无法识别旧端口时又可能生成 `Port OLD_PORT`。
- **方案**：列出旧端口声明所在文件及行号，生成 `sudoedit` 指引，要求清理旧声明后校验并 reload。无法唯一识别旧端口时阻止传统服务配置生成；显式 `--old-port none` 不生成占位 Port。socket 激活按实际监听验收，避免把被覆盖的 sshd 磁盘 Port 当成当前仍在监听。

### 7. 人工旧端口验证命令误判（BUG-032）

- **现象**：原生成 grep 模式含双重转义，可能没有匹配到实际仍在监听的 22，使操作者误认为已关闭。
- **方案**：改用 `sudo ss -H -ltn 'sport = :22'` 形式的端口过滤，明确只有命令成功且无输出才代表无 TCP 监听，命令执行失败不能算通过。原问题影响打印的人工验证指令，不等于脚本内部的监听解析也使用了该正则。

### 8. 恢复定时器漏检及低优先级一致性问题

- **BUG-033**：stage0 发现任何恢复 timer 就阻断，stage1/2 却只看 active。统一为运行、已启用或状态未知时阻断；inactive+disabled 仅保留信息。enabled+inactive 可在之后启动，不作为普通低优先级整理处理。
- **BUG-034**：自定义 backup-dir 缺校验和引用，创建备份还硬编码默认目录。改为校验非根目录的绝对路径，拒绝控制字符及 `..`，安全引用路径，创建与续跑都使用实际参数；恢复指令引用已采集的备份目录。
- **旧版痕迹**：补齐 stage2 的 `/usr/local/sbin/reinforce-my-ssh-firewall` 提示文件，与其它入口保持一致。
- **无用常量**：移除 stage1 未使用的 STAGE0 常量。

### 9. 远端密码登录状态尚未确认

原报告指出远端 `20-hardening.conf` 只看到 `PermitRootLogin no`，没有看到关闭密码登录。单个文件不能证明整体有效配置，更不能证明当前 sshd 进程已加载该配置。此次没有取得远端 sudo 密码或运行有效配置检查，因此仍需在远端用 `sudo sshd -T`（必要时带实际用户/来源的 `-C` 上下文）检查，并通过新公钥会话及密码登录拒绝测试确认；不在本地修复记录中写成已关闭。
